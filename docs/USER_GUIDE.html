results-tracker · user guide

Plan, run and publish a paper's experiments from one database

A guide to wiring results-tracker into an existing research repository and using its GUI as the dashboard for planning studies, tracking what has run, comparing results, and pinning the tables and figures that go into the manuscript.

results-tracker 1.x · branch recipe-layer · September 2026 · companion to docs/INTEGRATION.md and docs/RECIPES.md

Print with your browser's Print → Save as PDF. Each numbered section starts on a new page.

0Three ideas

Everything in the tracker is built from three objects. Once these are clear, every page and command is a view of one of them.

Run

One execution of one method on one dataset, optionally one instance (image) and one seed, with a config dict of every knob and a metrics dict of the numbers you would put in a table. Runs live in experiments; experiments in a project (one per paper).

Study

A planned experiment as data: which problem, which grid of conditions, which method arms, and either a swept knob or a full model plus single-knob ablation arms. A JSON file in studies/; the runner turns it into runs and resumes when interrupted.

Asset

One table or figure of the manuscript, pinned from a GUI view: experiment, filter and rendering options. The Paper page lists them, says when their data moved, and export paper regenerates all of them into stable file names.

The experiment type only decides how runs are grouped on screen: a comparison is methods × metrics, a sweep is one metric against one knob, an ablation is every single-knob change against the full model. Nothing else is declared up front; methods, datasets and metrics are created the first time they are logged.

1Connect an existing repository

Budget about an hour: install, decide where the database lives, instrument the one place your script already has the config, the metrics and the output folder, then import whatever results you already have.

1.1 Install into the environment your experiments run in

pip install -e ~/Documents/Research/results-tracker        # logging API only needs SQLModel
pip install -e "~/Documents/Research/results-tracker[ui]"   # adds Streamlit, Plotly, pandas, matplotlib

The GUI can live in a different environment from the experiments (a plain .venv without torch); section 2.3 explains how it still plans studies. One SQLite file per paper, next to the manuscript, works well:

export RESULTS_TRACKER_DB=~/Documents/Research/adaptivePnP-paper-workspace/results.db
results-tracker init

1.2 Declare metrics and methods once

results-tracker metric define psnr --unit dB --fmt .2f
results-tracker metric define nrmse --lower --fmt .4f
results-tracker method define dpir --label 'DPIR~\cite{zhang2021}' --baseline --position 1
results-tracker method define adaptive_pnp --label AdaptivePnP --position 9   # ours: last row

Direction decides what is bold, unit and format appear in every header and cell, labels carry the citation, and position fixes the row order of every table. All of this is also editable on the Settings page.

1.3 Instrument the script

The only call you need is log_run. Log the whole config, not just the varied knob, because ablations are computed as config diffs and a knob you did not log cannot be diffed. Metrics are numbers; put flags in config.

from results_tracker import log_run

log_run("deblur-main", project="adaptive-pnp", experiment_type="comparison",
        method=method, dataset="CBSD68", instance=f"img{idx:02d}", seed=seed,
        config={"K": K, "lambda": lam, "kernel": kernel, "noise": noise, "denoiser": denoiser},
        metrics={"psnr": psnr, "ssim": ssim, "runtime_s": t},
        artifacts_dir=str(out_dir))          # reconstruction.png, ground_truth.png, measurement.png

Re-running a script is safe: a run with the same experiment, method, dataset, instance, seed and config is a duplicate setting and is skipped, so n never inflates. Tag the full model of an ablation with tags=["base"]; change exactly one config key per variant.

1.4 Import what you already have

results-tracker import paper_results/metrics.csv -e deblur-main -p adaptive-pnp \
    --method-col method --dataset-col dataset --instance-col image_idx --seed-col seed \
    --config-col K --config-col kernel_idx --config-col noise_level --dry-run     # then without --dry-run
results-tracker import reported_baselines.csv -e deblur-main -p adaptive-pnp --source reported

Numbers copied from a paper go in as source=reported: they appear with n = 1 and no std, the audit lists the datasets they do not cover, and they get hollow markers in trade-off plots.

1.5 Open the GUI

results-tracker ui                       # uses $RESULTS_TRACKER_DB; falls back to a free port if 8501 is busy

The browser tab title names the database file. The sidebar has the database (with a dropdown of recently opened ones), the project, the experiment, the pooled experiments and the filter; these are one selection shared by every page and mirrored in the URL, so a view can be bookmarked or pasted into notes.

2Declare what the repository can run

The recipe layer lets the repository describe its methods and problems once, so comparisons, sweeps and ablations become specs instead of hand-written grid loops. A Method reconstructs; its behaviour is fully described by the knobs it declares. A Problem poses instances under conditions (kernel, noise, dose) and scores estimates.

2.1 A method and a problem

from results_tracker.recipe import Method, Problem, Knob, Estimate, Instance, registry

@registry.method
class AdaptivePnP(Method):
    key, label, citation = "adaptive_pnp", "AdaptivePnP", ""
    knobs = (Knob("algorithm", "choice", "pgm", choices=("pgm", "admm")),
             Knob("K", "int", 20, bounds=(1, 500), doc="iteration budget"),
             Knob("beta", "float", 0.5, bounds=(0.0, 1.0), doc="EMA weight"),
             Knob("reg_strength", "float", 1.0, bounds=(0.1, 10.0), log=True),
             Knob("denoiser", "choice", "drunet", choices=("drunet", "dncnn_blind")))
    def setup(self, problem, config):            # once per study per distinct setup_key
        return load_denoiser(config["denoiser"])
    def reconstruct(self, instance, config, state):
        x_hat, info = pnp_recon(instance.measurement, instance.forward, state, **config)
        return Estimate(x_hat, {"iterations": info["iters"], "curves": info["curves"]})

@registry.problem
class Deblurring(Problem):
    key = "deblurring"
    conditions = (Knob("kernel", "int", 0, bounds=(0, 11)), Knob("noise", "float", 0.03, bounds=(0.0, 0.2)))
    splits = ("test", "validation")
    metric_definitions = {"psnr": ("dB", True, ".2f"), "ssim": ("", True, ".3f")}
    def dataset_name(self, split): return "CBSD68" if split == "test" else "DIV2K"
    def instances(self, condition, split, n, seed): ...   # yield Instance(name, measurement, reference, forward)
    def metrics(self, estimate, instance): ...

Everything that changes a result is a knob; a knob that is set but not declared is an error. Numeric scalars in diagnostics become metrics of the run; a curves dict of per-iteration lists goes to the run's diagnostics.json, which the Curves page reads. The condition goes into every run's config next to the method's knobs, so tables can group by config.kernel and ablations pool over it.

2.2 Check the declarations

results-tracker recipe knobs adaptive_pnp -i adaptivepnp.recipes
results-tracker recipe validate studies/deblurring/compare-K5.json          # lists the jobs, runs nothing

2.3 Let the GUI plan without the compute environment

The GUI's environment often lacks torch or the data. Write the declarations next to the specs, from the environment that has them; the Studies page reads knobs.json whenever a spec's imports fail there.

conda run -n adaptivePnP results-tracker recipe export-knobs -i adaptivepnp.recipes -o studies/knobs.json

3Plan studies

A study spec is a JSON file under the project's studies directory (set it once on Settings → Project, or $RESULTS_TRACKER_STUDIES, else studies/ next to the database). The Studies page reads every spec there and compares it with the database.

{
  "name": "deblurring-ema-beta",  "kind": "sweep",  "project": "adaptive-pnp",
  "problem": "deblurring",  "imports": ["adaptivepnp.recipes"],
  "conditions": {"kernel": [0, 1, 2, 3], "noise": [0.03, 0.05]},
  "methods": [{"method": "adaptive_pnp", "config": {"algorithm": "admm"}}],
  "sweep": {"knob": "beta", "values": [0.0, 0.25, 0.5, 0.75, 1.0]},
  "split": "test",  "n_instances": 20,  "seeds": [0, 1],
  "feeds": ["fig:beta"],                              # the paper assets this study produces data for
  "artifacts_dir": "results/tracker_artifacts"
}

Every job runs on every instance of every condition and seed. A study over the whole kernel × noise grid that sweeps one knob is a sweep, not an ablation: the Sweep page plots the metric against the knob and pools or splits the conditions.

3.1 What the Studies page shows

  • Progress per spec: jobs, runs done / expected, failed, running, a progress bar, and time left (pending runs × the median runtime_s of the study's completed runs). The page sums the compute left over unfinished studies.
  • The grid: arms down, conditions across, each cell coloured done / running / partial / failed / missing. Completed is derived from the database with the same config fingerprint the runner's resume uses, so page and runner never disagree.
  • Feeds: which paper assets the study produces data for; the Paper page shows each asset's readiness from this.
  • Pending-only spec: a download of the spec narrowed to the unfinished part of its grid, to hand the rest to another machine that can reach the same database file. It resumes, so nothing is recomputed.
  • Edit / Clone: loads the spec into the form below, under its own file name or as a copy for the K = 2 / 5 / 10 family.

3.2 Planning a new study in the form

  1. Name, kind, project, problem, split, instances per job, seeds, description, and the asset labels it feeds.
  2. Conditions: one value or a comma-separated list per condition knob; the grid is their product.
  3. Method arms: pick the method, open its knobs, change only what differs from the defaults (only those are written to the spec).
  4. For a sweep, the swept knob and its values; for an ablation, one or several knobs per arm from widgets, with a label for a joint change.
  5. Read the job count, check the spec preview, Save spec. The page prints the command to run it.

4Run studies

results-tracker recipe run studies/deblurring-ema-beta.json --db paper/results.db
results-tracker recipe run studies/deblurring-ema-beta-pending.json --db paper/results.db   # the pending-only spec

Running is resumable: settings already logged as completed are skipped, failed ones are recomputed, and a crash or a non-finite estimate becomes a failed run with the message in its notes while the grid keeps going. While a setting computes, a running row stands in for it, so the Overview and the Studies grid show work in flight; a hard crash leaves that row visible instead of nothing. The runner never deletes anything.

Where things land: one run per instance in the database; images and diagnostics.json under <artifacts_dir>/<study>/<method>/<arm>/<condition>/<seed>/<instance>/; without an artifacts folder the diagnostics still go to <database>.diagnostics/. The runner also records the study's description and swept knob on the experiment, which the Sweep page and the Overview headline default to.

Two machines. The database is one SQLite file. Run where that file lives, or on a filesystem both machines can reach reliably; the pending-only spec is how you split a grid. The GUI can open the file read-mostly at the same time and picks up new runs on Refresh.

From a run_study call in Python you can also pass problem_options (device, data root: machine facts that stay out of the run config), provenance (a dependency's commit, appended to every run's notes) and observers that fire after each logged run.

5Look at results

Every experiment page loads the selected experiment, applies the sidebar filter, and drops failed runs from the numbers (they are counted on the Overview). The filter has the CLI's --where grammar, so anything you see can be reproduced on the command line: --where 'config.noise=0.01' --where 'config.K=[2,5]'.

5.1 Three habits that make tables honest

  • Pool deliberately. With several datasets the Comparison page keeps dataset as a row key by default. When you pool experiments with Also include experiments (the main table with K across columns from three studies), group by experiment or the config key that differs.
  • Name your groupings. A value map (Settings → Value maps) derives a labelled field from a raw one: config.kernel 0–3 → isotropic, 4–7 → anisotropic, 8–11 → motion becomes derived.kernel_type, usable as a row, column or filter key everywhere; columns follow the rule order.
  • Read the caption. Every on-screen table and figure carries an IEEE-style caption stating the aggregation unit, n, and what is pooled. If the caption surprises you, the table will surprise a reviewer.

6Publish the paper

Under every table and figure is a Pin to paper expander. It saves the current view as an asset: experiment, pooled experiments, filter and rendering options, with a LaTeX label (tab:main, fig:beta), a status and a caption. Pinning the same label again replaces what it renders and marks the old export as no longer current.

6.1 The Paper page

Assets in manuscript order with kind, status (planned / draft / final / dropped), experiments, filter, Data (completed / planned runs of the studies that feed it) and State: never exported, current, or stale when runs were added or replaced since the export. Edit status, order, label, caption and notes; Open in … restores the view on the page that configures it; Write to directory or a zip renders everything.

results-tracker export paper -p adaptive-pnp -o paper/assets      # tables/, figures/, data/, preamble.tex, MANIFEST.json
results-tracker asset list -p adaptive-pnp                         # which assets are stale
results-tracker asset set fig:beta -p adaptive-pnp --status final

In the manuscript, \input{tables/tab-main} and \includegraphics{figures/fig-beta}; the Makefile has one target. Never edit numbers in the generated files: every .tex starts with a provenance comment (database, experiment, run count, filter, timestamp) and a re-export replaces it.

assets:
	results-tracker export paper -p $(P) -o assets

7Keep the project organised

  • Stages. Settings → Experiments marks an experiment paper, exploratory or superseded. Superseded experiments leave every selector unless a sidebar checkbox shows them, so old attempts stop cluttering the menus without being deleted (results-tracker experiment set NAME -p P --stage superseded).
  • Notes. A dated line per decision on the Overview ("beta = 0.5 chosen: plateau in deblurring-ema-beta"), or attached to an asset on the Paper page so the reasoning sits next to the table it justifies (results-tracker note add).
  • Method order and primary metric. Settings → Methods fixes the row order of every table; Settings → Project sets the metric the Overview headline and default figures use, and the project's studies directory.
  • One database per paper, committed with the manuscript at the submitted revision; specs in studies/, committed with the code. Method keys are stable identifiers; display labels can change without touching runs.

8A working week

  1. Monday. Studies page: what is planned, what is done, how much compute is left. Clone last week's spec for the next K, save, run it where the GPU is.
  2. While it runs. Overview shows running rows; Curves shows whether the new arm behaves per iteration; a diverging condition shows up as a wide band and a 6 dB row on the Sweep page long before the grid finishes.
  3. When it finishes. Sweep → Selection picks the tuned value and writes it into the comparison spec; Comparison → Per instance ranks the images for the qualitative figure; Visual builds it with the same instance on every panel.
  4. Before the meeting. Pin the views that will be in the paper, set their status, add a note with the decision. export paper, rebuild the manuscript, and read the Paper page: nothing stale, everything final.
  5. Before submission. The audit on every table shows all cells present or the gaps are explained in the text; every claimed ablation component is clear; the sweep plateau matches the chosen default; panel metrics agree with the tables; MANIFEST.json goes in the supplementary material.
